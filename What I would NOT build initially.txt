And there's an even deeper question

You said:

"properly safe and secure and private"

We need to define exactly what private means.

There are at least five different threat models.

Level 1 — Protect against Wi-Fi/network attackers
TLS
Level 2 — Protect messages from your server
E2EE
Level 3 — Protect against compromised server

Need:

E2EE
+
authenticated device identity
+
key verification
Level 4 — Protect against stolen database

Need:

E2EE
+
encrypted message storage
+
minimal metadata
Level 5 — Protect against compromised endpoint

This is fundamentally different.

If:

Bob's laptop

is compromised, malware can potentially read:

"Hello"

after your application decrypts it.

No messaging protocol can magically solve a fully compromised endpoint.

This is one of the most important realities to understand.

The metadata problem

Here's something most people miss.

Even with perfect E2EE, your server might still know:

Alice
 ↓
Bob
 ↓
23:41
 ↓
message size = 147 bytes

It may potentially know:

who communicated
when
how often
message size
IP address
device information
online/offline status

So:

E2EE protects content. It does not automatically provide metadata privacy.

If your goal is truly extreme privacy, we need to design the metadata model separately.

An invite-only, multi-platform, end-to-end encrypted private messenger where cryptographic identity is tied to individual devices, the server acts primarily as an encrypted message relay/store-and-forward service, and message contents and attachment contents remain inaccessible to the server.

My current recommendation

Start with Flutter for the client, not a web app and not Electron.

Why?

Because your actual requirement isn't "desktop application."

It's:

One application that can move with the user between ARM mobile devices and ARM/x64 computers.

Flutter is explicitly designed for multi-platform native compilation and currently supports the platforms/architectures you care about.

Then make the security architecture protocol-first, not UI-first.

And don't invent the cryptography. We should evaluate an established protocol/implementation such as Signal-style cryptography versus Matrix's Olm/Megolm model before choosing the implementation. Matrix's current E2EE documentation, for example, explicitly covers device identity, one-time keys, sessions and ratcheted group encryption.

The next thing I'd design with you

Before writing one line of Flutter code, I would make a threat-model document containing exactly these:

1. Who can create an account?
2. Who can invite someone?
3. What does the server know?
4. What does the server NEVER know?
5. What happens if the database is stolen?
6. What happens if the server is compromised?
7. What happens if a phone is stolen?
8. What happens if a laptop is stolen?
9. How are devices verified?
10. How are keys backed up?
11. How does a new device join an account?
12. What happens when a device is revoked?
13. How are offline messages delivered?
14. How do multiple devices synchronize?
15. How do we handle attachments?
16. How do we handle disappearing messages?
17. What metadata do we retain?
18. How do we prevent spam/invitation abuse?
19. How do we handle push notifications without leaking message content?
20. What exactly does "private" mean for this application?
